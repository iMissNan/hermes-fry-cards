## 3. 外观、排版与视觉设计深度透视

### 3.1 卡片布局流向对比 (Layout Flow)
- **本地方案 (Local)**：
  - 流向：`[Header (流式阶段)] -> [Answer 正文] -> [统一面板: 思考过程 + 工具步骤] -> [Footer 状态栏]`
  - 设计意图：答案优先（Answer-First），正文永远在最上方第一时间展示给用户；冗长的思考链和工具输出作为折叠面板沉底，不抢占首屏阅读视线。
- **参考仓 A (aiduPOP)**：
  - 流向：`[Header] -> [Answer 正文] -> [统一面板: 思考 + 工具] -> [Footer]`
  - 核心特色：引入 **泡波 (Bubble-Wave)** 主题层，将飞书的标准图标映射为俏皮 emoji（例如：模型 `👸🏻`、思考 `🌊`、工具 `🫧`、耗时 `✨`、折叠提示 `💦 还有 N 项已折叠`）。
- **参考仓 B (lark-hls-v2)**：
  - 流向经过多次迭代（提交 `eb44775` 调换位置 -> `af665ba` 沉底）：最终稳定为 `Answer 正文 -> 分割线 -> 思考过程 -> Footer`。
  - 视觉样式集中收拢在 `card/styles.py` 的 `CardStyles` 数据类（统一控制灰色分割线、圆角 `5px`、面板行距 `4px`、内边距 `8px`）。

### 3.2 动态台词系统 (Repo B 独创特性)
- **代码出处**：`cmp-lark/lark-hls-v2/card/quotes.py` 与 `quotes_data.json`
- **设计逻辑**：
  - **场景识别引擎 (`detect_scene`)**：根据当前卡片状态（`has_reasoning`、`has_tools`、`is_sealing`、`is_error`）自动推断场景：`greeting`（问候）、`thinking`（思考）、`battle`（工具执行）、`victory`（成功完成）、`defeat`（失败）、`seal`（封印）。
  - **冷却防重复机制**：采用双端队列记录最近 10 次台词索引，防止连续两轮吐出相同语句。
  - **Header 标题注入**：在流式卡片顶部以引用形式展示经典动漫台词（火影、海贼、死神等），增强拟人化与趣味性。

### 3.3 Cron 定时任务卡片的外观与设计差距
- **本地与原仓现状**：
  - `build_cron_card` 极其简陋，固定使用 `template="blue"` 单色 Header，标题仅有任务名和时间，内容直接平铺 Markdown。
- **参考仓 B 优秀设计 (`docs/cron-card-design.md`)**：
  - **动态 Header 语义配色**：成功=绿色 (`green`)、失败=红色 (`carmine`)、重试/超时=黄色 (`yellow`)。
  - **超长输出折叠**：超过 5 行或包含大段输出时，主体内容自动包裹进 `collapsible_panel`，保证群聊内不会被大段巡检日志刷屏。
  - **结构化 Footer**：单行包含任务名称、调度表达式（`cron 0 3 * * *`）、耗时统计、以及失败告警连击数（`连续失败: N 次`）。

### 3.4 思考面板的碎片化合并 (<30 字符折叠)
- **痛点**：在多轮工具交互或模型快速碎碎念时，模型常输出 5~15 字的极短 thinking 片段。
- **Repo B 解决方案 (`f28f044`)**：
  - 在 `card/elements.py` 中引入 `MERGE_THRESHOLD = 30`。
  - 连续短片段累积进临时缓冲区，不单独生成面板 Header；仅当字数达到阈值或遭遇工具调用时才一次性 Flush 成块，面板高度减少 40% 以上，告别碎片感。

## 4. 系统级查漏补缺与缺陷台账 (P0 / P1 / P2)

### 🔴 P0 级（系统级假死、死循环与并发竞态）
1. **飞书 300315 `not find elementID` 导致加载占位符死循环**
   - **出处**：Repo A `feishu/client.py:151-160`、Repo B `feishu/client.py:178-187`
   - **根因**：网络重试时，占位符在服务端已丢失，客户端继续尝试删除或在之前插入，飞书抛 300315。本地未将其识别为非致命事件，导致卡在加载态。
   - **补丁方向**：在 `hermes_fry_cards/feishu.py` 增加正则过滤，遇到包含 `not find elementID` 的 300315 自动视为幂等成功。
2. **封卡 CAS 标志缺失 (`_completion_dispatched`)**
   - **出处**：Repo B `controller.py:691-697`
   - **根因**：并发打断与完成事件同时调度时，可能多次调用底层的异步完成协程。
   - **补丁方向**：在 `CardSession` 中增加 CAS 状态锁，确保单会话生命周期内仅触发一次终态封卡。
3. **封卡全局 30s 协程超时兜底**
   - **出处**：Repo B `card_flow.py:1436-1445`
   - **根因**：飞书 API 网关 Socket 假死时，封卡协程可能永久挂起。
   - **补丁方向**：`asyncio.wait_for(self._do_complete_card_inner(session), timeout=30.0)`。

### 🟡 P1 级（功能体验、边界异常与容错）
1. **开放平台 99991400 (per-API 频控限制) 未加入瞬态重试**
   - **出处**：Repo A `feishu/client.py:123`、Repo B `feishu/client.py:152`
   - **根因**：瞬间高频调用触发飞书 400 频控，被本地视为不可恢复错误上抛。
   - **补丁方向**：加入 `CARDKIT_TRANSIENT_ERROR_CODES`，走 0.5s 退避重试。
2. **超时后 `close_streaming` 幂等调用（消除跳动三个小点）**
   - **出处**：Repo B `card_flow.py:1113-1135`
   - **根因**：即使本地记录已关闭流式，服务端状态可能脱节，卡片仍有小点跳动。
   - **补丁方向**：封卡时无论本地状态为何，均带 `try...except` 强发一次关闭指令。
3. **超长失活会话二次终态清理 (2x TTL)**
   - **出处**：Repo B `controller.py:326-340`
   - **根因**：异常脱离主流程的会话在内存字典中残留。
   - **补丁方向**：巡检时发现 `age > 2 * session_ttl`，强制调用 `mark_failed("ttl_expired")` 彻底销毁。

### 🟢 P2 级（外观优化与代码卫生）
1. **思考过程短片段合并 (`MERGE_THRESHOLD = 30`)**：参考 Repo B 优化排版。
2. **Cron 定时任务卡片视觉重构**：引入红绿动态状态 Header 与输出折叠。
3. **飞书 200 元素上限精准递归计算**：借鉴 Repo A 的 `_count_tag_objects` 树遍历，杜绝复杂嵌套下的 300305 报错。

## 5. 安全性、破坏性风险与工程规范分析

1. **绝对禁止借鉴的破坏性行为**：
   - 参考仓 A 与 B 在启动时使用 `yaml.dump` 重写宿主 `~/.hermes/config.yaml`。这会洗掉老板本地配置的所有注释和缩进！本地的纯 AST 注入架构是最高效且零副作用的方案，坚决保留。
2. **仓外执行危险代码审计**：
   - 参考仓 A 残留的休眠代码指向仓外绝对路径，本地代码全链路封闭受控，零此类隐患。
3. **许可证与代码原创性**：
   - 所有外部仓库均遵循 MIT 许可。针对上述 P0/P1 问题，本地仅吸收其状态机转移算法与错误码判定规则，使用本地既有的 `SessionState` 与 `builder.py` 重新编写干净实现，保留清晰的出处溯源注释。
